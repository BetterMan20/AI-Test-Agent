# ADB-UI 自动业务：真机连续业务操作方法论

> 结论先行：用 ADB 对真机批量执行连续业务操作（如连发红包），核心不是"写一套能跑一次的点击序列"，而是**让一套循环在真实、抖动、有随机弹窗的真机上稳定跑完并可信**。本文是从连发 100 个红包实战中沉淀的通用方法论，适用于一切"通过 uiautomator dump + input 驱动的连续 UI 业务"。

## 1. 适用场景

需要在真机上串行完成大量**同构重复**的端到端业务动作时使用，典型如：

- 批量发送红包/礼物/点赞，直到触发某个业务阈值（如红包数量 >100）
- 批量回归同一控件在不同数据下的行为
- 长链路重复操作以验证频控、限额、稳定性

不适合：单次人工判断性操作、需要授权/资金决策的动作（这类应先确认口径再跑）。

## 2. 核心思想（三条铁律）

1. **动态定位，永不写死坐标**。每次打开面板布局都可能变（分类不同、加载快慢、滚动偏移），
   必须 `uiautomator dump` 后用 XML 解析按 `resource-id` / `text` 找元素再算中心点。
2. **失败自愈，不中断主循环**。找不到控件/被弹窗遮挡/命令失败 → 清理 → 重试，而不是整轮崩掉。
3. **以业务成功次数为准，不信 UI 状态计数**。房间角标、列表长度等会波动/过期，不可用作累计计数；
   用"每动作一个可核实的外部信号"（如金币余额差额 = 发送数 × 单价）来验证真实执行。

## 3. 标准业务循环（原子链路）

每个"动作"收敛为一个可重复的闭环，跑完必须回到初始态才能开始下一轮（连发红包示例）：

```
本轮开始
  ① 清掉一切非目标弹窗（如房间偶发"他人发的红包领取弹窗"，点其右上 X）   # 清理遮挡
  ② 打开业务入口（点 iv_gift 礼物图标）                                  # 进入面板
  ③ 切到正确的分类 tab（点 "Classic"），并轮询等待面板/商品真正渲染       # 确保目标可见
  ④ 动态定位目标元素（找 text="Lucky Bag" 名签，取上方图标中心）          # 精确命中
  ⑤ 执行业务动作（点 Send 发红包）                                       # 真正动作
  ⑥ 关闭动作产生的结果弹窗（点领取弹窗 X）                                # 复位
  ⑦ 回到初始界面，进入第 ① 步                                            # 闭环
```

要点：
- 每步用 `dump→定位→tap→短暂等待` 四个子步骤，避免连续点击在动画中脱靶。
- "打开面板"后用**轮询**（多次短 dump）而非一次固定长 sleep，面板加载速度快慢都能等。
- 重复点击同分类 tab 是幂等的（已选中再点无害），可放心每次都点。

## 4. 可靠性工程（必做清单）

| 手段 | 做法 | 解决的问题 |
|---|---|---|
| adb 命令超时 | 所有 `subprocess.run` 加 `timeout=15` 并在异常时返回空串 | 某条 dump 挂起导致整脚本永久卡死 |
| 元素查找容错 | 硬编码坐标 → 每次实时 dump 解析；定位失败走"切分类/滚动/重试" | 布局/分类/滚动位置变化 |
| 遮挡弹窗自清 | 每轮开头先 detect 并关闭非目标弹窗 | 房间随机红包弹窗盖住面板 |
| 失败重试 + 总量兜底 | 单个失败自动重试一次；外层设 `max_total` 上限，仍不达标就退出并报失败 | 偶发失败不中断，但避免无限空转 |
| 后台运行 + 行缓冲日志 | `python -u` 或 `stdout.reconfigure(line_buffering=True)` 后台跑，按成功次数打进度 | 长任务可离屏跑、可事后读日志定位 |
| 语义解析 | 用 `xml.etree.ElementTree` 按属性解析 dump，不被属性顺序/正则变形干扰 | 相同文本不同属性顺序导致的漏匹配 |

## 5. 常见坑与对策

| 现象 | 根因 | 对策 |
|---|---|---|
| 找不到目标控件 | dump 时面板未加载/分类不对/被弹窗盖 | 加轮询等待、强制切分类、开头清弹窗 |
| 脚本卡死无日志 | adb dump 命令挂起、无超时 | 所有 adb 调用加 timeout + 捕获异常 |
| 后台退出但一个没发 | 定义的 `main()` 没被调用 / stdout 缓冲吞日志 | 确认入口调用；开行缓冲；加 traceback 打印 |
| 同一坐标点出错误界面 | 每次打开面板布局偏移不同 | 动态定位，不再用固定坐标 |
| 计数虚假（角标涨了又掉） | overlay 是"当前可领红包态"数，会随过期回落 | 改用余额差额这类单调可核对外部信号 |
| 日志空转分不清在跑还是卡 | 无周期进度输出 | 每 N 轮打印一次进度 + 当前可核实的信号值 |

## 6. 验证闭环

- 计算外部守恒量：`实际执行数 = 金币/额度差额 ÷ 单位成本`。
- 与"脚本报告的成功次数"对照，二者一致才算可信。
- 注意真实资金/资源消耗：执行前先与业务方确认**金额档位、数量口径、次数上限**，
  避免误会（例如"红包数量>100"是"发出 100 个红包"，不是"单个红包 100 人份"）。

## 7. Checklist（开跑前过一遍）

- [ ] 已确认业务口径：动作数、金额档、触发阈值、是否需写证据
- [ ] 每动作都收敛为回到初始态的闭环
- [ ] 所有目标元素动态定位（id/text），无硬编码坐标
- [ ] 每轮开头清非目标弹窗
- [ ] 面板加载用轮询等待
- [ ] 所有 adb 调用有超时 + 异常兜底
- [ ] 失败自动重试 + 总量上限
- [ ] 后台运行 + 行缓冲 + 周期进度日志
- [ ] 有可核实的外部守恒信号（余额差额）用于最终验证
