2.2 整条目标链路（产物分层 · API + Appium/ADB + DB）

assets（需求/S0-KB 系统事实）
  │
S1–S3 设计管线 → 意图层 output/test_design.json（测试模型/场景/测试点/风险/覆盖，S5 回填 case_intents）
  │ S4 文档级 TC ── test_cases.json（中间形态，评审输入，非交付物）
  │ planner plan_from_test_case / plan / plan_from_capture，或 planner --all 批量汇聚
执行层 output/execution_plan.json（meta + plans[]：steps[]:{type, config, assertions, evidence_types} + traceability）
  │ 前置门禁 verification.PlanValidator.validate
  ▼
发动机 ExecutionRunner.run_plan()
  ├ _dispatch(step) 按 step_type 路由：
  │  · api → APIClient.request(method/path/headers/body/data/params)
  │  · db → DBClient.query|execute(query, params)
  │  · adb → ADBClient.shell(command)（设备控制 + 证据采集）
  │  · appium → 已接入 AppiumController（UI 业务操作：By.ID 定位/tap/输入，懒启动 server+session）
  │  · manual→ skip（返回 status=skip）
  │  · 未知 → error（No tool configured for step type）
  ├ _verify(step) 逐断言 → RuleVerifier.check → passed/failed
  └ _collect_evidence 按 evidence_types → EvidenceCollector.* → EvidenceStore.save
         api request/response/headers/execution四件套 · db query/snapshot/execution · adb command/output/execution + 截图/logcat · appium action/page_source/execution
  ▼
结果层 output/execution_result.json（TestCaseResult + ExecutionResult，自动判定 pass/fail/error）
  │ 失败 → output/defects/<tc_id>.{json,md} 缺陷草稿（fail=疑似产品缺陷 / error=疑似环境问题，人工确认后提单/PR）
  ▼
S7 报告与决策 python -m execution.report（runner 收尾自动调用）
  ├ 聚合：execution_result.json + defects → 业务归因分布（business_verdict）
  ├ 决策 Release Gate：release_gate.json（GO / GO_WITH_WARNINGS 环境归因 / NO_GO fail 或未决缺陷）
  └ 人读 execution_report.html（决策块 + 两层结论 + 缺陷区 + 人工核查清单）

三、分线说明

3.1 TC → Plan → 执行 线

test_cases.json → plan(test_case, capability=None) 确定性
                → plan_from_test_case(test_case, capability=APICapability) LLM（注入抓包 API 知识）
                → ExecutionPlan
                → [PlanValidator.validate]（前置门禁：步骤类型/配置完备/API来自Capability/断言来自TC）
      → ExecutionRunner.run_plan(plan, ctx)

汇聚直读（产物拆分链路）：
  python -m execution.planner --all --no-llm            # test_cases.json → output/execution_plan.json
  python execution/runner.py --plan-file output/execution_plan.json   # 跳过 TC→Plan 派生，直读执行

3.2 抓包 → 回放 线

Whistle 抓包 → WistleParser.find_endpoints → CapturedAPI
  → plan_from_capture(captured)（step=api，断言复现 status_code + ret）
  → 或 replay/capture_replay.py CaptureReplay（高层：scan → pick_successful → 原样回放）
  → 同一 ExecutionRunner 链路
项目经验：回放必须用 req_body_raw 原始字符串经 data= 发送，因 sign 按 h_ts+token+body 原始字节计算，任何重排都会 sign 失配（ret=-1）。plan_from_capture 目前用 req_body(dict) 组装，存在该隐患，回放建议走 CaptureReplay。

3.3 证据采集 线

EvidenceStore(base_dir) + EvidenceCollector(store)
  api → collect_api_evidence   (request / response / headers / execution 四件套)
  db  → collect_db_evidence    (db_query / db_snapshot / db_execution)
  adb → collect_adb_evidence   (adb_command / adb_output / adb_execution) + 按需 screenshot / logcat
  text/collect_text
  落盘 → EvidenceStore.save → Evidence.path 回填 StepResult.evidence_refs
