1. 项目目标与当前处境

项目最初目标是提升测试效率、保证测试质量。复盘后有一个诚实的判断：早期大量投入集中在 S1–S5 的「测试设计自动化」（把需求变成用例），而它在已有经验的团队里往往不是效率的直接杠杆，甚至新增评审负担。真正同时撬动效率和质量的，是 S6 执行/回归：一键回放、自动采证据、自动判结论，把手工回归的人时省下来，也把漏测/误判暴露出来。

因此本轮聚焦点从「生成更多用例」转向「把回归执行真正跑起来并拿出可复用的成果」。

在批量回归之上新增统一决策入口：给定"回归模式 + 待测业务点 + 风险等级"，先决策本次跑哪些层、跑多少，再分派给各层执行，最后聚合为一份统一报告。决策当前为确定性规则（可复现、无外部依赖），并预留 llm_hook 接口供后续接 LLM 动态决策。

闭环：决策器 → 分派器 → 聚合

7. ADB-UI 自动业务方法论

从真机连续业务操作（如连发红包）实战中沉淀的一套可复用方法，落盘为 execution/METHODOLOGY_ADB_UI.md，供后续一切"通过 uiautomator dump + input 驱动的高重复连续 UI 业务"参考。

三条铁律

  1. 动态定位，永不写死坐标——布局/分类/滚动随时变，必须 dump 后按 resource-id/text 解析再算中心点。
  2. 失败自愈，不中断主循环——找不到控件/被弹窗遮挡/命令失败 → 清理 → 重试，而不是整轮崩掉。
  3. 以业务成功次数为准，不信 UI 状态计数——房间角标等会波动/过期；改用「余额差额 = 发送数 × 单价」这类可核对外部信号验证。

标准业务循环（原子链路）

清非目标弹窗 → 开业务入口 → 切分类并轮询等渲染 → 动态定位目标 → 执行动作(Send) → 关结果弹窗 → 复位，闭环后才开始下一轮。

可靠性清单（本机踩坑对照）

坑对策

找不到目标控件轮询等面板加载、强制切分类、开头清遮挡弹窗

8. 结论与建议下一步

已确立的价值

  • 效率：回放→断言→采证据→出结论全自动，一次回归只需 python run_s6_execution.py，省手工逐条核对。
  • 质量：协议层/业务层两层断言治理「误判」，如实区分成功(1)与业务状态码(-1/-101)，可追溯证据逐条落盘。
  • 发现力：暴露「批量回放同一请求触发后端防重放」这一真实边界，这是手工测试常忽略、却是回归该抓的信号。
  • 可扩展性：三层解耦 + 适配器后，新增项目只需 projects/<proj>/adapters + 一份 config/projects/<proj>.yaml，Core 与 app 零改动；业务动作与引擎彻底分离。

已知局限

  • 26 条用例共用同一份抓包成功样本回放，遇后端防重放/限频会整体指向 ret=-1；要验证业务成功态，需冷却窗口或按用例换用抓包中不同的样本/token/数据。
  • ADB/UI 的「面板特征校验」依赖当前设备实况（是否有直播发红包），属现场观测而非确定性断言。

建议下一步

  1. 按用例换样本：把「模块级复用同一样本」演进为「按 TC 类型从抓包选语义匹配、签名不同的样本」，绕过防重放，验证真正业务成功态。
  2. 前端确定性：UI 面板校验改为「进入指定房间→主动触发展示红包/金币」的确定性动作链，弱化对设备实况的依赖。
  3. API 层换新 token：红包 E2E 的 Phase A 用账号健康巡检联动——发送前先用最新登录样本刷新 token 再回放，规避 ret=-11 会话失效。
  4. 沉淀为定时回归：把 S6 挂入定时任务，产出日/夜跑回归报告，让「效率与质量」持续被量化。
  5. 业务动作补前端判定：send_gift / enter_voice_room 目前为 API 抓包回放复现，可为每个动作追加 ADB/UI 层验证（沿用 ADB-UI 方法论），形成协议+前端双重证据。
